# Claude Learning Skills

[![License: CC BY-NC-SA 4.0](https://img.shields.io/badge/License-CC%20BY--NC--SA%204.0-lightgrey.svg)](LICENSE)
[![Commercial License Available](https://img.shields.io/badge/Commercial%20License-Available-blue.svg)](LICENSE-COMMERCIAL.md)

**プロジェクトが終わるたびに、AI エージェントが自分の挙動をふりかえり、改善案を「人間のゲートを通してから」反映する——自己改善の学習パイプライン。**

完了したプロジェクトを「やりっぱなし」にせず、そこから次回の挙動を改善する学習を取り出します。
ただし——**AI が自分でルールを書き換えることは許しません**。学習は段階的なゲートを通り、
最後は必ず人間が承認します。

---

## 解こうとしている問題 — 「AI に学習させたい、でも自分でルールを書き換えさせたくない」

AI エージェントに経験から学ばせたい、というのは自然な願いです。
しかし「学んだことを自分でスキルに反映する」エージェントは、放っておくと壊れます。

- **1 回の事例から一般化しすぎる** — たまたま 1 度うまくいった/失敗したやり方を「常に正しい」と思い込む
- **ユーザー固有の好みを普遍ルールにする** — ある人の好みを、全プロジェクト共通の鉄則にしてしまう
- **プロンプトが肥大化する** — 学習のたびにルールが増え、判断が遅く・曖昧になる
- **既存の良い挙動を壊す（回帰）** — 良かれと思った追加が、別の場面で成功していた振る舞いを潰す
- **反省文で終わる** — 「次はもっと丁寧に」のような、行動に変換できない曖昧な反省を量産する

これは、このリポジトリ全体が向き合ってきた問題——**「AI の実行力の高さが、そのまま事故の速さになる」**——の、
「学習」版です。だから答えも同じです。

> **ルールを「書いて渡す」のではなく、プロセスを「守らざるを得ない構造」にする。**

学習を 1 つのスキルに丸投げせず、**観測 → 抽出 → 提案 → 回帰検査**の多段ゲートに分解します。
各段は意図的に**「やりすぎない」**ことを核心に持ち、最後は人間がレビューします。
これが、暴走しない自己改善の作り方です。

---

## パイプライン全体像

```
   プロジェクト完了
         │
         ▼
 ┌──────────────────────────────────┐
 │ ① post-project-learning-engine    │   観測して、学習を When/Then で抽出
 │    → Learning Log                 │   ★ Candidate 止まり（恒久昇格させない）
 └──────────────────────────────────┘
         │  Learning Log が複数たまったら
         ▼
 ┌──────────────────────────────────┐
 │ ② skill-proposal-engine           │   横断分析・選別・スコアリングして反映先を決める
 │    → Skill Patch 提案             │   ★ すべてをスキル化しない（採用しない判断も出す）
 └──────────────────────────────────┘
         │  採用したい Patch
         ▼
 ┌──────────────────────────────────┐
 │ ③ skill-regression-checker        │   回帰・矛盾・肥大化・副作用を検査
 │    → Approve / Revise / Reject    │   ★ 無条件に承認しない（Negative/Edge も必ず試す）
 └──────────────────────────────────┘
         │
         ▼
   人間レビュー → 承認したものだけ、手で反映
```

各段は独立した Claude Code スキル（`context: fork`）として隔離実行され、
受け渡しは構造化されたレポート（Learning Log / Skill Patch / Regression Report）を経由します。
**パイプラインは提案までしか行いません。スキルへの実際の書き込みは自動化していません**——
それが安全装置の核心です。

## 含まれるスキル（3個）

| スキル | 役割 | 入力 → 出力 | ゲートの核心 |
|---|---|---|---|
| `/post-project-learning-engine` | 学習の**抽出** | 会話・作業ログ・成果物・ユーザー反応 → **Learning Log** | **Candidate 止まり**。恒久スキルに直接昇格させない |
| `/skill-proposal-engine` | 学習の**選別と提案** | 複数の Learning Log → **Skill Patch 提案** | **すべてをスキル化しない**。採用しない判断も明示する |
| `/skill-regression-checker` | 提案の**回帰検査** | Skill Patch 案・既存スキル → **採用可否の判定** | **無条件に承認しない**。副作用が大きければ Approve しない |

3 つに共通する設計思想は、**「やりすぎないことを、各段の存在理由にする」**ことです。
一般的な「AI に反省させる」アプローチが過剰な一般化・自己肥大に陥るのに対し、
このパイプラインは各段で**ブレーキ**を構造化しています。

---

### ① post-project-learning-engine — 学習を抽出する（反省文にしない）

プロジェクト完了後に、**成功条件を復元し、実際の進行との差分から学習を取り出す**スキルです。
目的は反省文ではなく、**次回の具体的な行動ルール**を作ること。

- 事実の再構成 → 成功条件の復元 → 実際の進行整理 → **差分分析（適合/不足/過剰/不明）** → 原因分類
- すべての学習を **When（発火条件）/ Then（行動ルール）** 形式に変換する
- 失敗だけでなく**成功要因も必ず抽出**する（検証済みの良い挙動からドリフトしないため）
- 各学習に**適用範囲・適用してはいけない範囲・確信度**を必ず添える
- 出力は `# Post-Project Learning Log`（9 セクション）

> 「次はもっと丁寧に確認する」は禁止。
> 「When: 依頼に『ざっくり』等の曖昧表現があり完成条件が不明なとき / Then: 完成版を作る前に目的・読者・出力形式を短く確認する」のように書く。

### ② skill-proposal-engine — どれをスキル化すべきか選別する

複数の Learning Log を横断的に分析し、**何を・どこに反映すべきか**を判断するスキルです。
目的は「全部スキルにする」ことではなく、**スキル化すべきでないものを除外する**こと。

- 学習項目を正規化 → **原因構造でクラスタリング** → 一般化可能性を判定（**Global / Domain / Local / One-off / Rejected**）
- 10 項目で**スコアリング**（再発性・影響度・一般性・行動可能性・検証可能性・例外の明確さ・整合性・コスト・配布可能性・肥大化リスク）
- 反映先を決定（スキル本体 / チェックリスト / ワークフロー / テンプレート / ツール使用ルール / 確認質問ルール / ローカルメモリ / ログ保持のみ）
- 安全・法務・医療・金融・セキュリティに関わる失敗は、**1 回でも**強く扱う例外則
- 出力は `# Skill Proposal Report`（Skill Patch 提案を含む 9 セクション）

### ③ skill-regression-checker — 既存を壊さないか検査する（採用前ゲート）

Skill Patch 等の更新案が、**既存の良い挙動を壊さないか**を検査する最終ゲートです。
目的は承認ではなく、**回帰・矛盾・過剰一般化・肥大化・副作用を見つける**こと。

- 更新案の意図再構成 → 差分特定 → **矛盾・重複検査** → **過去の成功パターンを壊さないか** → **過去の失敗を再発させないか**
- 各更新案に **Positive / Negative / Edge** の最低 3 テストシナリオを必ず作る
- 判定は **Approve / Revise / Reject / Human Review / Defer**。副作用が大きければ Approve しない
- 高リスク領域は Human Review を優先。Revise の場合は**修正版パッチを必ず提案**
- 出力は `# Skill Regression Check Report`（11 セクション）

## なぜ「多段ゲート」で「人間レビュー必須」なのか

学習を 1 つのスキルで「観測して即スキル化」させると、前述の失敗（過剰一般化・肥大化・回帰）が
**検査されないまま恒久ルールになります**。一度ルールに焼き込まれた誤った一般化は、その後の
すべてのプロジェクトに影響し続けます。これは不可逆に近いコストです。

そこで、**不可逆性の高い「恒久ルール化」の手前に、安いブレーキを何段も挟みます**。

| ステータスの段階 | 意味 |
|---|---|
| Raw | 観測されたまま。まだ何の判断もしていない |
| Candidate | 学習として抽出済み。ただし採用は未定 |
| Watch | 追加観測待ち。1 事例では一般化しない |
| Local | このユーザー/案件だけ。配布スキルには入れない |
| Human Review | 専門・リスク・配布判断が必要。人間が決める |

「観測 → Candidate 抽出 → 選別 → 回帰検査 → 人間レビュー」という段階を踏むことで、
**安い検証（読む・試す）を不可逆な一手（恒久ルール化）の前に厚く積む**——
これは行動の憲法「リスクに比例して検証を厚くする」の、学習プロセスへの適用です。

## 使い方（運用イメージ）

```
1. プロジェクトが一段落したら
   → 「今回のふりかえりして」     （① が起動、Learning Log を蓄積）

2. Learning Log が数件たまったら
   → 「学習を棚卸しして、どれをスキル化すべきか評価して」
                                  （② が起動、Skill Patch を提案）

3. 採用したい提案が出たら
   → 「この更新案を検査して」     （③ が起動、回帰・副作用を検査して採否判定）

4. ③ が Approve / Revise を返したものだけ、内容を確認して手で反映する
```

各スキルは `/post-project-learning-engine` のように明示的に呼ぶこともできますし、
上記のような自然な依頼で自動起動することも想定しています。

## Quick Start

```bash
git clone https://github.com/nob-git-dev/claude-skills.git
cd claude-skills/learning-skills
./scripts/install.sh
```

`install.sh` は **3 つの学習スキルを `~/.claude/skills/` に展開するだけ**です。
`settings.json` の変更は不要で、`CLAUDE.md` や他のスキルには一切触れません。
同名スキルが既にある場合のみ `.backup-learning-YYYYMMDD-HHMMSS/` へ自動バックアップします。

### このパックだけ取得（sparse-checkout）

```bash
git clone --no-checkout https://github.com/nob-git-dev/claude-skills.git
cd claude-skills
git sparse-checkout init --cone
git sparse-checkout set learning-skills
git checkout main
cd learning-skills
./scripts/install.sh
```

## [sdlc-skills](../sdlc-skills/) との関係 — 開発と学習で閉ループを作る

このリポジトリの [sdlc-skills](../sdlc-skills/) は、**1 つのプロジェクトを規律正しく完了させる**ためのものです。
learning-skills は、**完了したプロジェクト群から、その規律そのものを改善する**ためのものです。

```
        ┌──────────────── sdlc-skills ────────────────┐
        │  仕様 → 設計 → 実装 → レビュー → デプロイ     │   ← 1 件を規律正しく「やる」
        └──────────────────────────────────────────────┘
                          │ 完了
                          ▼
        ┌────────────── learning-skills ───────────────┐
        │  観測 → 抽出 → 提案 → 回帰検査 → 人間レビュー │   ← 経験から規律を「直す」
        └───────────────────────────────────────────────┘
                          │ 承認された改善
                          ▼
              次回の sdlc-skills / 各スキルへ反映
```

sdlc が「やる」を、learning が「やり方を直す」を担い、両者で**自己改善の閉ループ**になります。
どちらも思想は共通です——**人間がゲートを握り、安易な自動化に委ねない**。

## 設計原則

1. **学習は Candidate から始める** — 観測しただけで恒久ルールにしない
2. **やりすぎないことを各段の核心にする** — 抽出は Candidate 止まり、提案は選別、検査は不承認も辞さない
3. **人間がゲートを握る** — パイプラインは提案まで。スキルへの書き込みは自動化しない
4. **1 事例から一般化しない** — 再発と適用範囲を確かめてから昇格させる
5. **証拠・推測・不明を分ける** — 情報が足りなければ「不明」と明記し、推測で補完しない

## 注意事項

- これらのスキルは**提案と検査までを行うもの**です。スキル本体・チェックリスト・ワークフローへの
  実際の反映は、出力を確認のうえ**人間が手で行ってください**。
- スキルの出力（学習・スコア・採否判定）は**参考情報**です。最終判断は利用者にあります。
