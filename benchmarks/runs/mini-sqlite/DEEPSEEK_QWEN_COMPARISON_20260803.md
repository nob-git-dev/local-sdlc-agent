# Mini SQLite: DeepSeek / Qwen 比較

## 結論

今回の Mini SQLite 実験では、**DeepSeek + 現在のハーネス構成が、Qwen + 当時のハーネス構成より良い成績**だった。

特に重要な差は、同一の `SPEC.md` に対する固定済み独立テストである。DeepSeek版は84件をすべて完走・合格した。Qwen版は現在の同じ独立テストを再実行すると33件を実行した時点で5失敗・10エラーとなり、残り51件はモジュール収集エラーなどにより実行されなかった。

ただし、この結果だけから「DeepSeekというモデル単体がQwenより常に優秀」とは結論づけない。DeepSeek実験では、その後に追加されたステージ分割、artifact修復、独立テスト、失敗分類などの改善も利用している。

## 比較条件

| 条件 | Qwen版 | DeepSeek版 | 比較可能性 |
|---|---|---|---|
| Mini SQLite仕様 | 同一 | 同一 | 直接比較可能 |
| SPEC SHA-256 | `9bca9006...d3ac83` | `9bca9006...d3ac83` | 完全一致 |
| モデル | `qwen3.5-122b` | `deepseek-v4-flash-0731` | 異なる |
| モデルプロファイル | `qwen-agent` | `deepseek-v4-flash-agent` | 異なる |
| ハーネス世代 | 過去版 | 改善後の現在版 | モデル単体比較を妨げる要因 |
| 独立テスト | 今回、Qwen成果物にも同じ84件を再実行 | 実装ループ中と完了時に84件を実行 | 成果物比較として有効 |

## 結果比較表

| 評価項目 | Qwen版 | DeepSeek版 | 今回の優勢 |
|---|---|---|---|
| S01〜S09到達 | S09まで到達、最終runは`approved` | S09まで到達、独立JudgeもPASS | DeepSeek（証拠が強い） |
| Pythonコンパイル | PASS | PASS | 同等 |
| 自己生成テスト | 179 / 179 PASS | 140 / 140 PASS | 同等。件数だけでは品質比較不可 |
| 独立テスト全体 | 完走せず | 84 / 84 PASS | **DeepSeek** |
| 独立テスト実行内訳 | 33件実行: 18 PASS、5 FAIL、10 ERROR。51件未実行 | 84 PASS、0 FAIL、0 ERROR | **DeepSeek** |
| 独立合格確認率 | 18 / 84 = **21.4%** | 84 / 84 = **100%** | **DeepSeek** |
| 公開API契約 | `BTree`、`Result.rows_affected`、AST、record codec等で不一致 | 独立テストの契約に適合 | **DeepSeek** |
| Lexer契約 | token種別、値の型・大文字小文字・負数で不一致 | 独立Lexerテストに合格 | **DeepSeek** |
| CLI契約 | `.tables`、`.schema`、エラー出力で不一致 | 単発・対話CLIとも合格 | **DeepSeek** |
| 100件以上のB+Tree分割 | 同一の128件probeは未実施 | 128件でsplit・全件検索・再openを確認 | DeepSeekのみ実証済み |
| 永続化 | 自己テストでは合格 | 文ごとに別プロセスで再openし合格 | DeepSeekの証拠が強い |
| 破損DB検出 | 独立pagerテストをimportできず未確認 | `CorruptDatabaseError`を独立確認 | **DeepSeek** |
| 禁止依存 | 0件 | 0件 | 同等 |
| ResourceWarning | 179件は合格するが、未close警告を多数観測 | warningをerror扱いにしても140件合格、警告なし | **DeepSeek** |
| 独立最終判定 | 当時の内部runは`approved`、現在の独立84件では不合格 | 証拠専用の別API Judgeが13条件をPASS判定 | **DeepSeek** |

`独立合格確認率` はモデルの総合点ではない。次の式で、固定テスト全体のうち実際にPASSを確認できた割合だけを表す。

```text
独立合格確認率 = 独立テストでPASSした件数 / 独立テスト総数
```

Qwen版では `unittest` が33件を数え、その内訳が5失敗・10エラーだったため、PASSは `33 - 5 - 10 = 18` 件である。収集できなかった51件をPASSとは扱わない。

## 定性的比較

| 観点 | Qwen版 | DeepSeek版 | 判定 |
|---|---|---|---|
| 大きなartifactの形式安定性 | 過去runでも修復ループが必要 | JSON崩れ、Markdown fence、途中切れが頻発 | 両方に課題。定量比較不能 |
| 長い文脈への耐性 | 当時の条件が異なり比較不能 | 16,384 context境界を2回超過 | DeepSeek側に明確な制約 |
| 小タスクでの実装精度 | 完走実績あり | 命題単位に分けると高い成功率 | 今回はDeepSeekが良好 |
| 完全自律性 | 外部支援・ハーネス改善あり | ステージ再分割・汎用lint修正・証拠整理に外部介入あり | どちらも未達 |
| 実行時間・API総数 | 全工程の同条件データなし | 全工程の比較可能な集計なし | 比較不能 |

## 正しい読み方

今回、直接言えること:

1. 同一SPECから作られた2つの成果物を現在の独立テストで検証すると、DeepSeek版が大幅に良かった。
2. DeepSeek版は自己テストだけでなく、固定された外部契約と実動作probeでも完走した。
3. 現在採用している「小さなステージ分割 + 独立テスト + 修復ループ」は実際に効果があった。

今回だけでは直接言えないこと:

1. 同一ハーネス・同一プロンプト・同一予算でモデルだけを入れ替えた場合もDeepSeekが勝つか。
2. DeepSeekの方が短時間・少ないAPI callで完了するか。
3. 別種の課題でも同じ差が再現するか。

したがって、現時点の運用判断は **DeepSeekを主候補として継続評価する** が妥当である。モデル単体の優劣を確定するには、今後、現在の同一ハーネス・同一ステージ・同一予算でQwenを再走行する必要がある。
