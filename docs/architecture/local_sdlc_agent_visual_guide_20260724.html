01 / OVERVIEW

最初に結論

設計の核心、調査範囲、いまのコードが実際にどこまで動くかを最初に固定します。

中心思想は 生成 → 適用 → テスト ではなく、 可視前提 → 最小Artifact → 機械検証 → 証拠付き判定 → 失敗を型付けして再試行 です。
SOURCE OF TRUTH

SPEC.md が一次情報

固定要件を暗黙に変えず、足りない事実は推測せず UNKNOWN / MISSING_CONTEXT とする規律を全ロールに注入します。

ISOLATION

ロール間は文書交換

API呼び出し同士に共有記憶があると仮定せず、SPEC、PM文書、ファイル本文、コマンド結果を毎回明示します。

CONTROL KERNEL

Artifactを信用しない

LLM出力をそのまま書かず、プロトコル、対象パス、重複、ストリーム暴走、スコープ、意味契約を検査してから原子的に適用します。

VERDICT

成功は証拠の積

command_ok AND judge_approval が基本条件。初期状態ですでに受入条件を満たす場合は、無用な編集をせず終了します。

このレポートの読み方

実装済み Pythonコードで確認できる動作 Prompt規律 LLMに要求している振る舞い ルールベース キーワードや固定テンプレートによる判定 現行制約 テスト・汎用性・安全性上の注意

制御面

Pythonが決める

CLI引数、対象パス、予算、危険コマンド、Stage順序、失敗分類、再試行先、最終条件はランナー側が保持します。LLMに制御権を丸投げしません。

生成面

LLMは役割ごとに呼ぶ

03 / EXECUTION MODES

似ている4系統を区別する

このリポジトリを誤読しやすい最大の地点です。「文書を作る実行」と「コードを適用・検証する実行」は別物です。

入口主目的LLM呼び出しコード適用テスト向いている用途
supervisor タスク分類とSkill順序の決定 Supervisor + --execute時の各Skill しない Skill文書上の提案まで 計画・設計・レビュー文書を作る
supervise 旧式のPM → Coder → Judge文書交換 選択したStepごと しない 自動適用ループなし 役割分離Promptの確認・文書生成
agent 単一作業単位の実装・修復・判定 PM / DDD / Coder / Repair / Judge する コマンド・Smoke・意味Probe 実際にコードを変更したい
run-stages 仕様を複数Stageに分け、統合まで実行 Stageごとに独立Agent run する Stage gate + final gate SQLite/Redis/HTML系の段階構築
web 上記のローカルGUIラッパー 選択コマンドに従う 選択コマンドに従う 選択コマンドに従う CLI引数を安全なargvとして組み立てる
最重要: supervisor --execute は各Skillを実行しますが、その出力を agent のapply/testループへ自動配線しません。実ファイル変更が目的なら agent または run-stages が入口です。

Functional budget

既定 3 rounds

テストや意味要件の失敗に使う本体予算。単なるJSON崩れで消費しないよう分離されています。

Protocol + adaptive

1 + 2 rounds

既定Agentではprotocol修復1、failure scoreが縮む・新種の失敗へ進む場合のadaptive修復2。

Root-cause

既定 1 round

同じfailure signatureの反復後だけ解放。Stage実行ではprotocol/root-causeの既定値が2に増えます。

Round内の重要ルーチン

局面主な処理設計上の意味
開始artifact_path_policy(), collect_file_context(), python_public_symbol_ledger()書ける場所と、LLMが実際に見たコードを固定
生成前前Round文書、semantic contracts、repair advice、failure signatureを圧縮“忘れた会話”ではなく可視履歴を次入力にする
生成中artifact_stream_guard()応答完了まで待たず、壊れ方が証明できた時点で中止
適用snapshot_artifact_targets() → parse → apply → rollback複数Artifactの途中失敗で半端な編集を残さない
検証command、required paths、HTML/Redis smoke、mechanical probesLLMの自己申告ではなく観測可能な結果へ変換
修復exact/family signature、failure analysis、patch plan、policy triage同じ局所修正の無限反復を避け、対象・原因・所有を再定義
終了run.partial.json → run.json中断可能なcheckpointと最終truthを分離
よい設計点: 初期precheckが通る場合にCoderを呼ばないこと。Agentの目的を「必ず差分を作る」ではなく 「要件を満たした状態と十分な証拠を得る」と定義しています。

Stageごとに隔離されるもの

  • 書込み対象とreadonly context
  • 必要ファイルと自動テストコマンド
  • AgentのRunディレクトリ
  • Round予算と失敗証跡
  • 完了済みStageの短いsummary

COMMAND

- SPEC.md を一次情報として扱う。
- 固定要件を黙って変更しない。
- 日付、コマンド結果、テスト結果、ファイル内容、環境の事実を捏造しない。
  与えられたruntime factsと文書だけを使う。
- 具体的なコマンドと検証可能な受入条件を優先する。
- 破壊的または本番影響のある操作は進めず、人間の承認を求める。
- patchを求められた場合はunified diffだけを返す。

BUDGET

6,000 bytes

REPETITION

8 / 40 / 80

Guardが即座に止める代表例
  • 最初のArtifactより前に長い説明・思考・進捗実況が続く

  • 同じJSON artifactや同文が反復した
  • orphan marker、nested conflict marker、未閉鎖blockが確定した
  • searchとreplaceが同一、または全Python moduleを局所repairとして出した
  • strict semantic repairで2 file目・2 block目へ進んだ

専用Smoke checks

HTML / Tetris

closing tags、inline JavaScriptをNodeでsyntax check。Tetris語彙では関数名、200 cells、初期render sequence、Chromium interactionまで追加します。

Redis

空portでserverを起動し、PING、ECHO、SET/GET、TTL、invalid input、複数clientをRESP wire protocolで検査します。

専用SmokeとAcceptance mappingは強力ですが、HTML/Tetris・Redis・SQLite寄りの知識がコードに埋め込まれています。 一般アプリの意味要件を自動で証明するframeworkではありません。未知領域では明示テストとrequired pathを利用者が与える必要があります。

--resume はmanifestと直近最大8文書を読み、別API呼び出しへ明示挿入します。

Copy worktree

--copy-worktree は一時コピー上でAgentを動かし、承認後に許可pathだけ原projectへ戻します。.git、.sdlc-runner、bytecodeは除外されます。

これはGit worktreeではなく shutil.copytree ベースです。また現行コードでは作成した一時directoryの自動削除が見当たらず、長期運用ではcleanup方針が必要です。

技術評価と次に読む場所

このプログラムの価値は“賢いモデル”より“間違えるモデルを扱う制御設計”にあります。

強いところ

  • SPECと可視文書だけを根拠にする明確なepistemic boundary
  • PM/Coder/Judgeの責務とAPI呼び出しを分離
  • Artifact-only contractをPython parser/guardで実際に強制
  • protocol failureとfunctional failureの予算分離
  • transactional applyとrollback
  • failure signatureからroot cause pathへ昇格
  • 強いruntime evidenceが弱いproxyを上書きするモデル
  • Run文書による監査・再開・比較
  • 外部Python packageなしで起動できる小さな配布面

設計負債になりやすいところ

  • 2巨大moduleに規則・例外・domain-specific heuristicが集中
  • Stage/acceptanceが特定デモ領域に寄る
  • Prompt内のaspirational capabilityとruntime capabilityが混在
  • 安全性がprocess isolationではなく主に文字列policy
  • 現行テストが宣言Python範囲でgreenではない
  • 一部のrepair grammarが増殖し、相互作用の理解コストが高い
