結論: agent基盤は「ローカルLLMが不安定でも、失敗を観測・分類・拒否・巻き戻しながら前進する」 方向へ進化しています。一方で、現在のLLM単体は長いコード修正でハルシネーションが多く、 ハーネス側の制約・検証・rollbackが必須です。

各役割は同じ会話の中の「気分」ではなく、API callを分け、system promptレベルで独立させる設計です。 スーパーバイザーは直接コードを書かず、仕様、証拠、失敗分類、許可パス、禁止パスを通じてcoderを制御します。

インタラクティブ解説

1. Stage分割大きい仕様をS01...S09へ分割
スーパーバイザーが一度に全部作らせず、ステージ単位で必要ファイル、テスト、完了条件を渡します。
2. Role-separated API callsPM / coder / judge / analysisをAPI call単位で分離
役割ごとに温度、token budget、thinking設定を変えられる構造です。
3. Artifact-only制御coderは文章ではなく機械適用可能なartifactを返す
BEGIN_FILE、BEGIN_SEARCH_REPLACE、JSON artifacts、unified diffなどを受け付け、曖昧な出力は拒否します。
4. Apply前検査静的lintとプロジェクトポリシーで危険な修正を拒否
テスト改変、存在しないAPI追加、禁止された修正対象、壊れたartifact形式を弾きます。
5. 実行証拠テスト、smoke、mechanical probeを証拠化
失敗はログとして保存され、次ラウンドの命題と制約になります。
State S = (Spec, Stage, Context, Artifacts, Evidence, Constraints) Goal: find patch p such that Verify(Apply(p, Project)) = PASS Safety invariants: I1: Artifact round is atomic Apply(A1...An) = all_success OR no_project_change I2: Evidence paths are readonly unless policy triage permits path ∈ readonly => patch(path) = reject I3: Generated tests are mutable evidence, external SPEC is authoritative contradiction(test, SPEC) => repair_test_or_reject, not broaden_product I4: LLM proposes, runner disposes LLM_output => lint => apply => verify Failure transition: fail_signature = normalize(test_result) if repeated(fail_signature): call failure_analysis derive required_paths, readonly_paths, forbidden_paths restrict next artifact

数理化の狙いは、LLMに自由作文をさせることではなく、短い命題へ分解して機械判定可能な制約に落とすことです。 例: 「rows exist before close but disappear after reopen」なら、CLI表示ではなく永続化境界を修正対象にする、という形です。

制御分類目的今回の効果
Stream Guard形式壊れたartifactを生成途中で早期停止nested conflict markerを検出し、無駄な長時間出力を止めた
Transactional Apply安全性1ラウンドのartifactを全成功/全不変にする後続artifact失敗時の部分適用残りを防ぐ
Failure Analysis意味失敗を構造化JSON化し、次のrequired_pathsを出すCLI失敗をrow persistence問題として分類
Project Policy Triage意味テストが外部仕様かagent生成物かを判断誤った生成テストを無条件に正典扱いしない
Artifact Normalization形式軽微なJSON/関数断片の崩れを機械的に補正単一関数置換へ安全に昇格
Unknown self attribute lint安全性存在しないself属性の導入を拒否self._pager / self._btree型の幻覚を次回から止める
Semantic Contracts意味仕様命題を実行ログに残し次ラウンドへ渡す禁止対象やreadonly evidenceを継続

LLMの弱点

長い既存コードの一貫理解が弱く、存在しない属性/APIを作る、禁止方向へ戻る、形式を壊す、という傾向が出ました。

ハーネスの価値

LLMを信頼して直接適用するのではなく、提案をlint、検証、rollback、failure analysisで囲うことで前進可能になります。

S09はまだ完走していませんが、失敗が「CLIが悪い」から「row persistence境界が悪い」へ狭まり、 さらに「存在しない属性を使う修正は拒否すべき」という一般化された改善につながりました。

2. より強い属性/API検査
ASTベースで存在しないメソッド・属性・importを検出する。
3. ステージ再開戦略
S09全体ではなく、row persistence修復だけを小さいstageとして切り出す。
