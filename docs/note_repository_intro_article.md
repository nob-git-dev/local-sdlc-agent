# ローカルLLMで動く「仕様書駆動のコーディングエージェント」を公開しました

GitHub:

https://github.com/nob-git-dev/local-sdlc-agent

## これは何か

`Local SDLC Agent` は、ローカルLLMを使ってソフトウェア開発を進めるためのコーディングエージェントです。

ただし、「AIにコードを書いてもらうだけ」のツールではありません。

このプロジェクトで重視しているのは、AIに丸投げすることではなく、AIが間違える前提で、仕様・実装・検証・失敗分析をきちんと分けて進めることです。

言い換えると、AIを「賢い作業者」として扱うのではなく、ソフトウェア開発プロセスの中に組み込まれた部品として扱います。

## なぜ作ったか

AIに開発を任せると、たしかに速く動くものができます。

いわゆる Vibe Coding 的な体験です。自然言語で頼むと、コードが出てくる。小さなツールなら、それで十分なこともあります。

しかし、少し複雑なものを作り始めると、問題が出てきます。

- 仕様を勝手に補完する
- テストしていないのに「動きます」と言う
- 一度間違えた仮説を何度も繰り返す
- 失敗ログを見ているようで、実際には読めていない
- 生成したテスト自体が間違っているのに、製品コードを直そうとする
- コードの出力形式が壊れて、そもそも適用できない

こうした問題は、単に「もっと賢いモデルを使う」だけでは消えません。

もちろんモデル性能は重要です。しかし、LLMは確率的に出力するシステムなので、外側に検証構造が必要です。

そこで、仕様書を中心にしながら、複数の役割を分け、実行証拠を保存し、失敗を分析し、修正ループを制御するための基盤を作りました。

## Local SDLC Agent の考え方

中心にある考え方は、かなり単純です。

「AIが守るべきルールをプロンプトに書く」のではなく、「守らざるを得ない構造にする」。

そのために、Local SDLC Agent では、開発をいくつかの役割に分けています。

- PM: 仕様、制約、受け入れ条件を整理する
- Coder: 仕様と文書に基づいて変更パッチや生成ファイルを作る
- Judge: 実装結果を仕様と証拠から評価する
- Failure Analysis: 同じ失敗が続いたときに原因を構造化する
- Project Policy Triage: テストを直すべきか、製品コードを直すべきかなどを分類する

これらは同じ会話の中で混ぜて実行するのではなく、別々のAPI呼び出しとして実行します。

それぞれの役割には別々の system prompt を与えます。つまり、PM、Coder、Judge が同じ文脈で自己正当化し続けるのではなく、文書を介して情報を受け渡します。

## 「文書でつなぐ」という設計

このエージェントでは、会話履歴ではなく、保存された文書が次の判断材料になります。

実行すると、`.sdlc-runner/runs/` の下に次のようなファイルが残ります。

- PM の判断
- Coder の出力
- 適用された変更パッチや生成ファイル
- テスト結果
- 受け入れ条件との照合
- 失敗分析
- Judge のレビュー
- `run.json` による実行全体の記録

これは単なるログではありません。

次のLLM呼び出しに渡す入力でもあります。つまり、エージェント同士は「なんとなく前に話したこと」ではなく、保存された証拠文書を通じて引き継ぎます。

この仕組みによって、AIの思い込みや自己評価を少しずつ外へ追い出し、人間にも追跡できる形にしています。

## 生成物とは何か

このプロジェクトでは、LLMが出力して runner が検査・適用するものを「生成物」と呼んでいます。

たとえば次のようなものです。

- unified diff
- ファイル全体の生成
- search/replace 形式の変更
- JSON 形式の変更指示

重要なのは、LLMが出したものをそのまま信用しないことです。

Local SDLC Agent は、生成物の形式、対象パス、安全性、テスト結果を runner 側で確認します。LLMには判断や提案をさせますが、最終的な適用や承認は機械的な検査を通します。

## 実際に何ができるか

現時点では、研究プレビューという位置づけです。

完成した商用アプリというより、ローカルLLMでコーディングエージェントを動かすための基盤です。

たとえば、次のような用途を想定しています。

- ローカルLLMでコード生成を試したい
- 仕様書ベースでAIに段階開発させたい
- AIの失敗ログを分析したい
- モデルごとの挙動を比較したい
- 企業内エージェントの安全設計を検討したい
- PM / Coder / Judge のような複数ロール構成を試したい

リポジトリには、Tetris や Mini SQLite、Redis風KVS などのベンチマーク例も含めています。

## 使い始めるには

ローカルLLMの OpenAI 互換APIが起動している前提で、次のように使います。

```bash
git clone https://github.com/nob-git-dev/local-sdlc-agent.git
cd local-sdlc-agent

python3 local_sdlc.py doctor --skip-llm
python3 local_sdlc.py list-skills
python3 local_sdlc.py health
```

ローカルLLM APIの標準URLは次の想定です。

```text
http://localhost:30000/v1
```

別のURLを使う場合は `--base-url` で指定できます。

## このプロジェクトの価値

私がこのプロジェクトで価値があると考えているのは、単に「コードを書くAI」ではありません。

価値の中心は、AIが失敗する前提で、外側に制御構造を作るところにあります。

- 仕様書を中心にする
- 役割を分ける
- API呼び出しを分ける
- 実行証拠を残す
- 受け入れ条件と照合する
- 失敗を分類する
- 同じ失敗を繰り返さない
- LLMに直接適用権限を渡さない

このような構造は、ローカルLLMがまだ不安定な場合ほど重要になります。

モデルが完璧ではないなら、外側のプロセスを強くする。これが Local SDLC Agent の基本思想です。
